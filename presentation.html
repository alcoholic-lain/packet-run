SOAP vs REST

Two ways to build web APIs

Ahmed Ridha LAZHARI · 3IA5

What they are

SOAP

A protocol. Messages are XML envelopes, the contract is a WSDL file, and extensions like WS-Security are standardized.

REST

An architectural style. Resources have URLs, HTTP verbs act on them, and JSON is the usual payload.

Key terms

TermMeaning
SOAP envelopeThe XML wrapper holding a message’s header and body
WSDLXML file describing a SOAP service’s operations and types
ResourceA thing an API exposes, identified by a URL
StatelessEach request carries all the context the server needs
OpenAPIA spec format for describing REST endpoints
IdempotentRepeating a call has the same effect as making it once

Side by side

AspectSOAPREST
FormatXML onlyJSON, XML, others
ContractWSDL, requiredOpenAPI, optional
TransportHTTP, SMTP, othersHTTP
CachingLimitedBuilt into HTTP
SecurityWS-SecurityHTTPS, OAuth
ErrorsFault elementHTTP status codes

Same request, two styles

SOAP

POST /UserService
<soap:Envelope>
  <soap:Body>
    <GetUser>
      <id>42</id>
    </GetUser>
  </soap:Body>
</soap:Envelope>

One endpoint. The operation lives inside an XML envelope.

REST

GET /users/42
Accept: application/json

The URL names the resource. The HTTP verb is the action.

Same failure, two styles

SOAP

<soap:Fault>
  <faultcode>soap:Client</faultcode>
  <faultstring>User not found
  </faultstring>
</soap:Fault>

Errors travel in a Fault element inside the message.

REST

HTTP/1.1 404 Not Found

{ "error": "User not found" }

The HTTP status code carries the outcome.

Choose SOAP when

Strict contracts

Both sides need a formal, machine-checked interface.

Built-in standards

Message-level security and reliable messaging are required.

Enterprise legacy

Banks, telecoms and older systems already speak SOAP.

Choose REST when

Public APIs

Easy to learn, test and call from any client.

Web and mobile

Light JSON payloads and HTTP caching keep apps fast.

Fast iteration

Loose contracts let teams evolve services quickly.

Things to avoid

With SOAP

  • Choosing it for a simple public API
  • Hand-writing XML instead of generating clients from the WSDL
  • Changing the WSDL without versioning it

With REST

  • Verbs in URLs, like /getUser
  • Returning 200 for errors instead of proper status codes
  • Storing session state on the server

Takeaway

REST is the default. SOAP earns its place where formal contracts and built-in standards matter.
